# 도지는 왜 MSA를 선택했을까?

저희 도지는 현재 MSA 구조로 시스템을 구축하고 있어요. 출발점은 각자 개발하던 WMS와 상품관리 서비스를 하나의 시스템으로 연결하자는 아이디어였죠.

이때 저희가 중요하게 생각한 건 이미 나누어진 업무 범위와 배포 단위를 유지하는 일이었어요. 두 서비스를 어떻게 통합할지 고민한 과정과, MSA를 선택한 뒤 고려하게 된 설계 문제들을 이야기해볼게요.

## 도지의 출발점

도지는 좌씨가 개발하던 WMS(창고 관리 시스템) 서비스와 제가 개발하던 상품관리 서비스를 통합해보자는 아이디어에서 시작했어요. 상품관리 프로젝트에서 다루던 프랜차이즈 카페를 바탕으로, 상품과 창고 운영을 아우르는 기업 시스템을 구축하는 것이 목표였죠.

두 프로젝트를 연결하기로 했지만, 코드를 어떻게 구성할지는 별개의 문제였어요. 기존 기능들을 하나의 애플리케이션으로 합칠 수도 있고, 별도 서비스로 유지하면서 API나 이벤트로 연결할 수도 있었어요. 저희는 기획 단계부터 두 방식의 장단점을 비교하기 시작했어요.

## 모놀리스로 통합하면 어떨까?

처음 나온 의견은 각 프로젝트의 기능을 하나의 모놀리스 애플리케이션으로 합치자는 것이었어요. 코드를 한곳에 모으면 전체 구조와 서로의 개발 진행 상황을 파악하기 수월할 거라고 생각했죠.

모놀리스는 여러 업무 기능을 하나의 애플리케이션으로 구성해 함께 배포하는 방식이에요. 개발 초기에는 다음과 같은 이점이 있어요.

- **개발과 검증을 시작하기 쉽다**: 여러 서비스를 연결할 환경 없이 하나의 애플리케이션에서 전체 흐름을 실행하고 테스트할 수 있어요.
- **배포와 운영이 비교적 단순하다**: 배포 대상이 하나이므로 여러 서비스의 버전과 상태를 함께 관리하는 부담이 적어요.
- **기능 간 호출이 단순하다**: 같은 프로세스 안에서 함수나 메서드로 협력할 수 있어, 서비스 간 네트워크 통신에서 생기는 지연과 실패를 다룰 필요가 줄어들어요.

다만 배포 단위를 공유한다는 제약도 있어요. 일부 기능만 수정해도 전체 애플리케이션을 다시 배포해야 하고, 특정 기능에 부하가 집중되더라도 일반적으로 애플리케이션 전체를 확장해야 해요. 같은 프로세스에서 자원을 공유하므로 한 기능의 과도한 자원 사용이나 프로세스 장애가 다른 기능에도 영향을 줄 수 있고요.

그렇다고 모놀리스의 모든 기능이 반드시 강하게 결합되는 것은 아니에요. 업무별 경계를 명확히 나누고 의존 관계를 관리하면 하나의 애플리케이션 안에서도 책임을 분리할 수 있어요. 저희가 기존 프로젝트에서 지향하던 모듈러 모놀리스도 그런 구조예요.

> [!TIP] 모듈러 모놀리스
> 하나의 애플리케이션으로 배포하면서, 내부에서는 업무별 경계를 명확히 나눈 구조를 말해요. 단순히 폴더나 패키지를 나누는 것만으로는 충분하지 않아요.
>
> - 각 모듈의 책임이 명확해야 해요.
> - 외부에 공개하는 기능과 내부 구현을 구분해야 해요.
> - 모듈끼리는 공개된 계약을 통해 협력해야 해요.
> - 허용하는 의존 관계를 정하고 경계 위반을 관리해야 해요.

저희가 모놀리스로 통합하지 않은 가장 큰 이유는 **기존 서비스의 배포 독립성을 유지하고 싶었기 때문**이에요. 이미 서로 다른 업무를 담당하는 프로젝트가 있었고, 각각의 내부에서도 모듈별 경계를 나누어 개발하고 있었어요. 이 상황에서는 하나의 배포 단위로 합치기보다, 각자의 책임을 유지하면서 연결하는 방식이 더 적합하다고 판단했어요.

## MSA로 연결하기

MSA는 Microservice Architecture의 약자로, 시스템을 업무별 서비스로 나누고 각 서비스를 독립적으로 배포·운영하는 것을 지향하는 구조예요. 서비스들은 API나 메시지로 협력해 하나의 업무 흐름을 구성하죠.

예를 들어 주문, 상품관리, 재고관리를 별도 서비스로 구성하면 각 서비스의 변경과 확장을 따로 진행할 수 있어요. 다만 독립성이 얼마나 확보되는지는 서비스 경계와 통신 계약을 어떻게 설계하느냐에 따라 달라져요.

모놀리스와 MSA의 주요 차이를 정리하면 다음과 같아요.

| 비교 항목    | 모놀리스                                      | MSA                                                 |
| ------------ | --------------------------------------------- | --------------------------------------------------- |
| 배포         | 애플리케이션 전체를 하나의 단위로 배포        | 서비스별 독립 배포를 지향                           |
| 기능 간 통신 | 주로 같은 프로세스 안에서 함수 호출           | API나 메시지를 통한 네트워크 통신                   |
| 확장         | 일반적으로 애플리케이션 전체를 확장           | 부하가 집중되는 서비스를 개별 확장 가능             |
| 데이터 관리  | 하나의 DB를 공유하는 구성이 일반적            | 서비스별 데이터 소유권과 접근 경계를 관리           |
| 트랜잭션     | 단일 DB에서 여러 기능의 변경을 묶기 쉬움      | 서비스 간 변경에는 별도의 일관성·복구 설계가 필요   |
| 장애 영향    | 프로세스 장애가 여러 기능에 영향을 줄 수 있음 | 장애 격리가 가능하지만 호출을 통해 전파될 수도 있음 |
| 개발·테스트  | 전체 흐름을 로컬에서 검증하기 비교적 쉬움     | 서비스 간 계약과 통합 흐름을 검증할 환경이 필요     |
| 운영·디버깅  | 배포 대상과 실행 흐름이 비교적 단순           | 여러 서비스의 배포·로그·상태를 연결해 관리해야 함   |
| 기술 선택    | 애플리케이션의 공통 기술 스택 안에서 선택     | 서비스별 선택이 가능하지만 관리 비용이 증가         |

### MSA 구조에서의 핵심 고려사항

서비스를 분리하면 개발과 배포의 자율성을 확보할 수 있지만, 그만큼 서비스 사이에서 결정해야 할 일이 늘어나요. 저희도 각 서비스의 내부 구현뿐 아니라 책임, 계약, 실패 상황을 함께 고민해야 했어요.

#### 서비스의 책임과 경계

먼저 어떤 업무와 데이터를 어느 서비스가 소유할지 정해야 해요. 모놀리스에서도 경계 설계는 중요하지만, MSA에서는 경계를 넘는 호출에 네트워크 통신이 필요하므로 잘못 나눈 경계가 더 큰 조율 비용으로 이어질 수 있어요.

상품의 이름과 가격을 관리하는 업무와 재고 수량을 관리하는 업무는 같은 상품을 다루더라도 책임이 달라요. 데이터의 원본과 변경 권한을 가진 서비스를 정하고, 다른 서비스는 공개된 계약을 통해 필요한 정보를 사용해야 하죠. 상대 서비스의 테이블을 직접 수정하면 그 서비스의 내부 구조에 의존하게 되어 독립적인 변경이 어려워져요.

서비스를 얼마나 작게 나누는지보다 함께 변경되는 업무를 적절한 경계 안에 모으는 것이 중요해요. 작은 기능 하나를 바꿀 때마다 여러 서비스를 동시에 수정하고 배포해야 한다면 경계를 다시 살펴볼 필요가 있어요.

#### 서비스 간 통신과 계약

여러 서비스가 협력하려면 어떤 정보를 어떤 방식으로 주고받을지 정해야 해요. API의 요청·응답 형식뿐 아니라 오류의 의미, 이벤트 내용, 계약을 변경할 때의 호환성도 여기에 포함돼요.

처리 결과를 받아야 다음 단계로 진행할 수 있는 업무에는 동기 호출을 고려할 수 있어요. 변경 사실을 전달한 뒤 각 서비스가 따로 처리해도 되는 업무에는 비동기 이벤트가 적합할 수 있고요. 동기 호출에서는 상대 서비스의 지연과 장애를, 비동기 처리에서는 반영 지연과 메시지 중복·순서를 다뤄야 해요.

서비스마다 배포 시점도 달라요. API 필드를 없애거나 이벤트의 의미를 바꿀 때는 기존 계약을 사용하는 서비스가 계속 동작할 수 있는지 확인해야 해요. 계약이 바뀔 때마다 모든 서비스를 함께 배포해야 한다면 독립 배포의 이점도 줄어들어요.

#### 데이터 일관성과 업무 복구

서비스별로 데이터를 관리하면 여러 서비스의 변경을 하나의 DB 트랜잭션으로 묶기 어려워져요. 한 작업은 성공하고 다음 작업은 실패할 수 있으므로, 어디까지 즉시 일관성이 필요하고 어디까지 반영 지연을 허용할지 정해야 해요.

예를 들어 주문·재고·결제가 별도 서비스인 시스템에서는 다음과 같은 흐름을 생각할 수 있어요. 도지의 현재 구현이 아닌, 복구 과정을 설명하기 위한 예시예요.

```text
주문 생성 → 재고 예약 → 결제 처리
                          ├─ 승인 → 주문 확정
                          └─ 거절 → 재고 예약 해제 → 주문 취소
```

결제가 거절되어도 이미 성공한 재고 예약이 자동으로 되돌아가지는 않아요. 예약을 해제하는 보상 작업이 필요하고, 그 작업마저 실패하면 다시 시도하거나 운영자가 확인할 수 있도록 상태를 남겨야 하죠. 정상 흐름과 함께 중간 실패 이후의 복구 과정도 업무로 정의해야 해요.

#### 부분 실패와 장애 전파

네트워크 통신에서는 상대 서비스가 정상이어도 응답을 받지 못할 수 있어요. 재고 예약 요청의 응답이 오지 않았다면 예약 자체가 실패했을 수도 있고, 예약은 성공했지만 응답만 유실되었을 수도 있어요.

이때 다시 요청하더라도 같은 예약이 중복 반영되지 않도록 해야 해요. 같은 업무 요청을 여러 번 처리해도 결과가 중복되지 않게 하는 특성을 멱등성이라고 해요. 재시도할 오류와 횟수, 응답을 기다리는 제한 시간인 타임아웃도 함께 정해야 하죠.

서비스 분리가 장애를 자동으로 격리해주는 것도 아니에요. 느려진 서비스를 계속 호출하면 대기 중인 요청이 쌓이면서 호출한 서비스까지 영향을 받을 수 있어요. 반복되는 실패에 대한 호출을 잠시 차단하는 서킷 브레이커나, 영향을 받는 기능만 제한하는 대응을 고려할 수 있어요.

#### 독립 배포를 위한 검증과 운영

서비스별 테스트가 통과해도 전체 업무 흐름이 올바르다고 보장할 수는 없어요. API와 이벤트가 합의한 계약을 지키는지 확인하는 계약 테스트와, 여러 서비스를 연결해 업무 흐름을 확인하는 통합 테스트가 필요해요.

운영 중에는 하나의 요청이 여러 서비스를 거칠 수 있어요. 어디에서 지연이나 실패가 발생했는지 찾으려면 요청을 연결해서 볼 수 있는 식별자와 로그, 처리 시간과 오류율 같은 지표가 필요해요. 서비스 간 실행 흐름을 확인하는 분산 추적도 도움이 되고요.

각 서비스의 내부 구현을 모두 알 필요는 없더라도, 하나의 업무가 어떤 서비스를 거쳐 수행되는지는 이해해야 해요. 서비스별 빌드·테스트·배포를 자동화하고 실패한 배포를 되돌릴 절차도 마련해야 독립 배포를 운영에서 활용할 수 있어요.

### 이런 부담에도 MSA를 선택한 이유

저희에게 가장 중요했던 건 기존 프로젝트의 업무 경계와 배포 단위를 유지하면서 개발을 이어가는 것이었어요. 상품관리와 WMS의 내부 책임은 정해져 있었지만, 두 서비스를 연결할 구체적인 업무 흐름은 아직 정하지 않은 상태였죠.

그래서 우선 각 서비스를 도지커피의 요구사항에 맞게 발전시키고, 연동이 필요한 업무가 구체화될 때 API와 이벤트 계약을 정의하기로 했어요. 새로운 업무가 별도의 책임을 가진다면 그 책임을 맡는 서비스도 추가하는 방향이었고요.

이 선택에는 운영 부담이 따랐어요. 그럼에도 기존 두 프로젝트를 하나로 재구성하는 작업과 배포 일정의 조율을 줄일 수 있다는 점을 더 중요하게 보았어요. 개발 속도와 유지보수 측면에서 이 방식이 저희 상황에 적합하다고 판단한 거예요.

> _물론 MSA를 한번 해보고 싶은 욕심도 조금 있었어요…_ 😅

## 현재 도지의 시스템 현황

MSA를 선택한 뒤, 상품관리 서비스는 도지커피에서 판매할 메뉴와 상품을 정의하는 카탈로그 서비스로 발전시켰어요. WMS는 원두·부자재·포장재 등 카페 운영에 필요한 품목을 다루도록 명세를 재정리했고요.

함께 합의한 요구사항을 바탕으로 각자의 프로젝트에서 개발을 이어갔어요. 서비스 내부의 변경은 각자가 맡고, 다른 서비스에 영향을 주는 계약의 변경은 함께 조율했죠. 상대 서비스의 모든 구현이 끝나기를 기다리기보다, 먼저 정한 인터페이스 명세를 기준으로 각자의 기능을 개발할 수 있었어요.

### 업무별로 나누는 서비스의 책임

기존 서비스를 다듬는 동안 인증, 매장 운영, 재고 예약 같은 업무도 구체화했어요. 현재는 다음과 같은 책임으로 나누어 설계와 구현을 진행하고 있어요.

| 서비스                                                             | 담당하는 책임                                                                                      |
| ------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------- |
| [Dozy Catalog](https://github.com/dozycoffee/dozy-catalog-api)     | 상품의 이름·가격·옵션·카테고리, 상품 상태와 판매 범위를 관리해요.                                  |
| [Dozy WMS](https://github.com/dozycoffee/dozy-wms-api)             | 창고의 입고·출고·반품·실사·폐기 등 원부자재를 실제로 다루는 작업을 맡아요.                         |
| [Dozy Inventory](https://github.com/dozycoffee/dozy-inventory-api) | 재고 수량과 예약을 관리하고, 추가로 예약할 수 있는 수량을 판단해요.                                |
| [Dozy Auth](https://github.com/dozycoffee/dozy-auth)               | 직원·점주·서비스 계정의 인증과 토큰 발급을 맡고, 토큰 검증용 공통 라이브러리를 제공해요.           |
| [Dozy Store](https://github.com/dozycoffee/dozy-store-api)         | 매장 정보·영업 상태·매장 매니저와, 매장별 상품의 진열·노출·품절 상태를 관리하도록 설계하고 있어요. |

WMS와 Inventory는 모두 재고와 관련되어 있지만 책임이 달라요. WMS는 창고에서 수행하는 작업을, Inventory는 재고 수량과 예약 가능 수량을 다뤄요. 여러 서비스가 재고를 조회하거나 예약할 때는 Inventory를 공통 기준으로 삼도록 설계하고 있어요.

Auth는 요청자가 누구인지, 어떤 역할을 가졌는지 보증해요. 그 사람이 특정 상품을 수정하거나 특정 매장을 관리할 수 있는지는 해당 업무 서비스가 판단하죠. 공통 인증과 개별 업무의 권한 판단을 나누는 방식이에요.

### 계약을 기준으로 연결하기

[Store의 요구사항](https://github.com/dozycoffee/dozy-store-api/blob/main/docs/requirements.md)에서는 Catalog가 상품 정의와 판매 범위를, Store가 매장별 진열과 노출 설정을 관리하도록 책임을 나누었어요. Store는 Catalog의 상품 이벤트를 받아 판단에 필요한 정보를 유지하고, 메뉴를 보여줄 때 필요한 상품 정보는 Catalog에서 조회하도록 설계했죠.

본사가 상품 정보를 바꾸는 작업과 매장 매니저가 진열 순서를 바꾸는 작업을 각자의 책임 안에서 구현하고, 두 서비스가 주고받는 정보는 API와 이벤트 계약으로 맞추는 방식이에요.

연동 범위도 단계별로 나누었어요. Store는 먼저 Catalog 연동을 기준으로 1단계를 구성하고, 재고 연동은 2단계로 계획했어요. 1단계에서는 매장 매니저가 품절을 직접 관리하고, 재고 연동 이후에는 재고 추적 상품의 품절 판단을 재고 기준으로 전환할 예정이에요.

운영 화면은 [Dozy Admin Console](https://github.com/dozycoffee/dozy-admin-console)에서 별도로 개발하고 있어요. 본사와 창고 운영자가 사용하는 통합 관리자 화면으로, 서비스별로 나누어진 기능을 업무에 맞게 제공하는 역할을 해요.

## 앞으로 확인할 것들

현재 도지는 서비스별 설계와 구현을 이어가며 연동을 구체화하는 단계예요. 저희가 지금 체감하는 이점은 각자의 업무 범위를 유지하면서 개발하고, 새로운 책임과 연결 지점을 점진적으로 정할 수 있다는 점이에요.

앞으로는 합의한 계약이 실제 연동에서도 맞는지, 통신이 지연되거나 일부 작업이 실패했을 때 업무가 어떻게 복구되는지 확인해야 해요. 독립 배포와 운영의 이점 역시 실제로 서비스를 연결하고 운영하면서 검증해나갈 생각이에요.
