서비스를 나누면 개발은 독립적으로 할 수 있지만, 운영은 오히려 늘어납니다.

도지커피 프로젝트는 `dozy-auth`, `dozy-inventory-api`, `dozy-wms-api`, `dozy-catalog-api` 같은 백엔드 서비스로 나뉘어 있습니다. 지금은 각자 로컬에서 띄워 개발하고 있지만, 이 서비스들을 한 환경에 함께 올려 서로 호출하게 하려면 "누가, 어디에, 몇 개를, 어떻게 띄울 것인가"를 정해야 합니다.

이 글에서는 MSA 운영에서 반복해서 나타나는 문제를 정리하고, 쿠버네티스가 각 문제를 어떤 리소스로 해결하는지 살펴보겠습니다. 그리고 도지커피 프로젝트에서 관리형 쿠버네티스에 서비스를 올리기 위해 `dozy-infra`에 정리한 설계를 예시로 들겠습니다.

> [!NOTE]
> `dozy-infra`는 아직 설계와 저장소 뼈대 단계입니다. 이 글에 나오는 구성은 실제로 클러스터에 올려 확인한 결과가 아니라, 올리기 전에 정한 설계입니다. 아직 확인하지 못한 부분은 마지막에 따로 정리했습니다.

## 1. 서비스를 나눈 뒤 생기는 운영 문제

모놀리스는 배포 대상이 하나입니다. 서버 몇 대에 애플리케이션 하나를 올리면 됩니다.

MSA에서는 같은 일을 서비스 수만큼 해야 하고, 서비스끼리 서로를 찾아 호출해야 합니다.

| 운영 문제        | 구체적인 상황                                                                                            |
| ---------------- | -------------------------------------------------------------------------------------------------------- |
| 독립 배포와 롤백 | inventory만 새 버전으로 바꾸고, 문제가 생기면 inventory만 되돌려야 합니다.                               |
| 장애 복구        | 프로세스가 죽거나 응답하지 않으면 사람이 보기 전에 다시 띄워져야 합니다.                                 |
| 서비스 찾기      | wms가 inventory를 호출하려면 주소를 알아야 하는데, 인스턴스가 바뀔 때마다 주소도 바뀝니다.               |
| 외부 노출        | 브라우저가 접근해야 하는 것과 내부에서만 쓰는 것을 구분해야 합니다.                                      |
| 설정과 비밀값    | DB 비밀번호나 서명 키를 이미지에 넣지 않고 주입해야 합니다.                                              |
| 개별 확장        | 부하가 몰린 서비스만 인스턴스를 늘려야 합니다.                                                           |
| 장애 원인 추적   | 요청 하나가 여러 서비스를 거치므로, 어디서 느려지거나 실패했는지 로그·지표·추적으로 볼 수 있어야 합니다. |

서버에 직접 올리고 스크립트로 관리할 수도 있지만, 서비스가 늘수록 이 목록을 사람이 맞추는 부담이 커집니다. 쿠버네티스는 이 반복 작업을 선언한 상태에 맞추는 방식으로 대신해 줍니다.

## 2. 쿠버네티스를 이해하는 핵심: 선언한 상태를 유지한다

쿠버네티스는 컨테이너를 여러 서버에 걸쳐 배치하고 관리하는 오케스트레이터입니다. 다만 개별 명령을 실행하는 도구라기보다, **원하는 상태를 선언하면 그 상태를 계속 유지하려는 시스템**에 가깝습니다.

```text
사람: "inventory를 3개 띄워 둔다" 라고 선언
        │
        ▼
컨트롤러: 현재 상태와 선언한 상태를 계속 비교
        ├─ 2개뿐이면 → 1개 더 생성
        └─ Pod 하나가 죽으면 → 새로 생성
```

이 구조가 앞에서 본 운영 문제 대부분의 바탕이 됩니다. 사람이 "죽으면 다시 띄운다"는 절차를 직접 실행하는 대신, "3개가 떠 있어야 한다"는 상태를 선언하는 것입니다. 이 선언은 YAML 파일(매니페스트)로 작성합니다.

먼저 자주 만나는 리소스를 간단히 정리하겠습니다.

| 리소스            | 역할                                                                         |
| ----------------- | ---------------------------------------------------------------------------- |
| Pod               | 컨테이너를 실행하는 가장 작은 단위입니다. 서비스 인스턴스 하나에 해당합니다. |
| Deployment        | 같은 Pod를 몇 개 유지할지, 어떻게 새 버전으로 바꿀지 선언합니다.             |
| Service           | 여러 Pod 앞에 붙는 고정된 이름과 주소입니다.                                 |
| Ingress           | 클러스터 밖의 요청을 어느 Service로 보낼지 정합니다.                         |
| ConfigMap, Secret | 일반 설정과 비밀값을 이미지 밖에서 주입합니다.                               |
| HPA               | 부하에 따라 Pod 수를 자동으로 조절합니다.                                    |
| Namespace         | 리소스를 논리적으로 나누는 경계입니다. 권한과 네트워크 정책의 단위가 됩니다. |

## 3. 문제별로 보는 쿠버네티스의 해법

### 3.1 독립 배포와 롤백: Deployment

Deployment는 어떤 이미지를 몇 개 띄울지 선언합니다. 이미지 태그를 바꾸면 쿠버네티스가 새 Pod를 띄우고 기존 Pod를 순서대로 교체합니다. 이것을 롤링 업데이트라고 합니다.

도지커피 프로젝트의 설계에서는 다음과 같은 전략을 기본으로 잡고 있습니다.

```yaml
strategy:
  type: RollingUpdate
  rollingUpdate:
    maxUnavailable: 0
    maxSurge: 1
```

- `maxSurge: 1`은 새 Pod를 하나 더 띄워도 된다는 뜻입니다.
- `maxUnavailable: 0`은 새 Pod가 준비되기 전에는 기존 Pod를 내리지 않는다는 뜻입니다.

레플리카가 1개여도 교체하는 동안 서비스가 끊기지 않게 하려는 설정입니다. 문제가 생기면 이전 버전으로 되돌릴 수 있고, 서비스마다 Deployment가 따로이므로 inventory만 교체해도 wms에는 영향이 없습니다.

다만 이런 무중단 교체는 readiness probe가 정확해야 성립합니다. probe가 없으면 컨테이너가 시작되기만 해도 준비된 것으로 보고 트래픽을 보내기 때문에, 앱이 아직 기동 중인데 기존 Pod가 내려가 요청이 실패할 수 있습니다. probe는 다음 절에서 다룹니다.

한편 이미지 태그를 정하는 규칙도 중요합니다. 이 프로젝트에서는 `latest`나 `main` 같은 움직이는 태그를 쓰지 않고, 릴리스된 서비스는 `X.Y.Z`, 아직 릴리스 전인 서비스는 `sha-<7자리>`로 고정하는 방향입니다. 한 번 빌드한 이미지를 그대로 배포해야 "지금 떠 있는 것이 무엇인가"를 추적할 수 있기 때문입니다.

### 3.2 장애 복구: probe

Deployment는 Pod가 사라지면 새로 만듭니다. 하지만 프로세스가 살아 있어도 응답하지 못하는 상태는 쿠버네티스가 스스로 알 수 없습니다. 이를 알려 주는 것이 probe입니다.

| probe     | 질문                              | 실패하면                                                       |
| --------- | --------------------------------- | -------------------------------------------------------------- |
| liveness  | 이 프로세스가 살아 있는가?        | 컨테이너를 재시작합니다.                                       |
| readiness | 지금 요청을 받을 준비가 되었는가? | Service의 대상에서 제외합니다. 재시작은 하지 않습니다.         |
| startup   | 기동이 끝났는가?                  | 성공하기 전에는 liveness와 readiness 검사를 시작하지 않습니다. |

도지커피 프로젝트의 백엔드는 Spring Boot이므로 Actuator의 헬스 엔드포인트를 probe에 연결할 계획입니다.

```yaml
livenessProbe:
  httpGet:
    path: /actuator/health/liveness
    port: management
readinessProbe:
  httpGet:
    path: /actuator/health/readiness
    port: management
```

다만 서비스마다 준비 상태가 다릅니다.

- `inventory`는 liveness와 readiness 엔드포인트가 따로 있습니다.
- `wms`는 현재 actuator가 없어 probe를 걸 수 없습니다. 먼저 서비스 코드에 actuator를 추가해야 합니다.
- `wms`는 기동할 때 Kafka에 연결해야 해서 시간이 걸립니다. 이때 liveness가 먼저 실패해 재시작이 반복되지 않도록 `startupProbe`가 필요합니다.

쿠버네티스를 도입한다고 서비스 쪽 준비가 필요 없어지는 것이 아닙니다. 쿠버네티스가 서비스의 상태를 판단하려면 서비스가 판단 근거를 제공해야 합니다.

probe를 설계할 때는 liveness에 DB 같은 외부 의존성을 넣지 않는 것이 좋습니다. DB가 잠시 느려진 것만으로 모든 Pod가 재시작을 반복하면 장애가 더 커지기 때문입니다. 외부 의존성은 readiness에서 확인하고, liveness는 프로세스 자체가 살아 있는지만 확인합니다.

### 3.3 서비스 찾기: Service와 내부 DNS

Pod는 교체될 때마다 IP가 바뀝니다. 호출하는 쪽이 Pod IP를 직접 알고 있으면 배포할 때마다 깨집니다.

Service는 여러 Pod 앞에 고정된 이름을 붙이고, 요청을 살아 있는(readiness가 통과한) Pod로 나눠 보냅니다. 클러스터 안에서는 다음과 같은 이름으로 호출합니다.

```text
<서비스>.<namespace>.svc
예) inventory.app.svc
```

도지커피 프로젝트에서도 서비스 사이 호출에 이 이름을 사용할 계획입니다.

| 호출                            | 방식                        |
| ------------------------------- | --------------------------- |
| wms → inventory                 | HTTP (`INVENTORY_BASE_URL`) |
| inventory → wms                 | HTTP (`WMS_BASE_URL`)       |
| wms, inventory, catalog → auth  | JWT 검증을 위한 JWKS 조회   |
| inventory, wms, catalog → Kafka | 클러스터 안 Kafka 브로커    |

이 주소들은 코드가 아니라 환경변수로 주입합니다. 로컬에서는 `localhost`를, 클러스터에서는 내부 DNS 이름을 넣으면 됩니다.

내부 이름으로 호출할 수 있다고 해서 모든 주소를 내부 이름으로 바꿀 수 있는 것은 아닙니다. 예를 들어 JWT를 검증하는 서비스는 토큰의 발급자(`iss`) 주소를 기준으로 공개 키(JWKS)를 조회하는 경우가 많습니다. 발급자가 `https://auth...` 같은 공개 주소로 찍힌 토큰이라면, 검증하는 서비스도 같은 공개 주소로 JWKS를 조회해야 할 수 있습니다. 그러면 클러스터 안의 서비스끼리의 호출인데도 외부 로드밸런서를 거치는 순환 경로가 생깁니다.

이런 경우에는 발급자 주소와 JWKS 조회 주소를 따로 지정할 수 있는지, 또는 클러스터 안에서만 공개 도메인을 내부 Service로 연결하도록 DNS를 구성할 수 있는지 확인해야 합니다.

### 3.4 외부 노출: Ingress와 관리 포트 분리

도지커피 프로젝트 설계의 원칙은 **외부에서 보이는 것은 로드밸런서 하나뿐**이라는 것입니다. 서비스, DB, Kafka, 관측 도구는 모두 프라이빗 네트워크 안에 둡니다.

```text
브라우저
   │ HTTPS
   ▼
외부 로드밸런서 (+ 관리형 TLS 인증서)
   │
   ▼
Ingress ──┬─> auth
          ├─> wms
          ├─> inventory
          └─> catalog
```

여기서 한 가지 규칙이 중요합니다. **`/actuator/*`는 Ingress로 노출하지 않습니다.**

Actuator에는 헬스 체크뿐 아니라 메트릭처럼 외부에 공개하면 안 되는 정보도 있습니다. 그런데 기본 설정에서는 이런 엔드포인트가 업무 포트에서 함께 열리는 경우가 많아서, Ingress에서 경로를 막지 않으면 그대로 노출될 수 있습니다. 그래서 이 프로젝트에서는 모든 백엔드가 `management.server.port`를 업무 포트와 다른 포트로 두는 것을 표준으로 정했습니다.

| 포트      | 용도               | 연결                                                   |
| --------- | ------------------ | ------------------------------------------------------ |
| 업무 포트 | 사용자 요청        | Service와 Ingress                                      |
| 관리 포트 | probe, 메트릭 수집 | NetworkPolicy로 kubelet과 Prometheus만 접근하도록 제한 |

Ingress에서 경로를 막는 것은 실수하기 쉽습니다. 처음부터 포트를 분리하면 Service와 Ingress에 관리 포트를 연결하지 않는 것만으로 외부에는 노출되지 않습니다. 다만 클러스터 안의 다른 Pod는 관리 포트에 접근할 수 있으므로, 이 부분은 NetworkPolicy로 따로 제한해야 합니다.

### 3.5 설정과 비밀값: ConfigMap, Secret

이미지에 환경별 값이나 비밀값을 넣으면 환경마다 이미지를 다시 빌드해야 하고, 비밀값이 이미지에 남습니다. 이 프로젝트에서는 값의 성격에 따라 보관 위치를 나눴습니다.

| 값                                           | 보관                     | 주입 방식                                                |
| -------------------------------------------- | ------------------------ | -------------------------------------------------------- |
| 일반 설정 (주소, 포트, CORS origin)          | 매니페스트의 ConfigMap   | 환경변수                                                 |
| DB 비밀번호, system client secret, SMTP 자격 | 클라우드의 비밀값 저장소 | External Secrets Operator가 쿠버네티스 Secret으로 동기화 |
| auth 서명 키 (RSA PEM)                       | 클라우드의 비밀값 저장소 | 읽기 전용 볼륨으로 마운트                                |

쿠버네티스의 Secret 객체는 값을 base64로 인코딩할 뿐이라, 읽을 수 있는 사람에게는 값이 그대로 드러납니다. 그래서 Secret에 대한 접근 권한을 제한하고, 원본은 외부 저장소에서 따로 관리합니다.

인프라 저장소가 공개이므로 비밀값을 저장소에 넣지 않는 것이 특히 중요합니다. 비밀값은 클라우드의 비밀값 저장소에만 두고, 배포 스크립트는 값이 없으면 중단할 뿐 값을 직접 만지지 않습니다.

### 3.6 개별 확장: replicas, HPA, PDB

서비스를 독립적으로 확장하려면 Deployment의 `replicas`를 서비스별로 조절하면 됩니다. 부하에 따라 자동으로 조절하려면 HPA(Horizontal Pod Autoscaler)를 사용합니다.

다만 모든 서비스를 똑같이 늘릴 수는 없습니다. 프로젝트의 서비스는 확장에 대한 조건이 서로 다릅니다.

| 서비스    | 시작 replicas                 | 확장 조건                                                                                                                                                                           |
| --------- | ----------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| auth      | 1 (고정)                      | 요청 제한이 인메모리이고 `@Scheduled` 작업이 있어서 늘리려면 요청 제한 상태를 공유하는 Redis와, 스케줄 작업을 한 인스턴스에서만 실행하게 하는 ShedLock 같은 잠금 도입이 먼저입니다. |
| inventory | 1에서 시작, 2~3으로 확장 실습 | 다중 인스턴스에 안전합니다. 부하 테스트로 HPA를 실습합니다.                                                                                                                         |
| wms       | 1                             | 스케줄러가 여러 인스턴스에서 안전한지 코드 확인이 필요합니다.                                                                                                                       |
| catalog   | 1에서 시작                    | 예약 적용 배치는 예약마다 잠그고, 이벤트를 DB에 먼저 저장했다가 발행하는 아웃박스는 한 번에 한 인스턴스만 발행하도록 되어 있어 안전합니다.                                          |

쿠버네티스가 Pod를 늘려 주는 것과, 서비스가 Pod가 늘어나도 올바르게 동작하는 것은 별개입니다. 두 인스턴스가 같은 스케줄 작업을 동시에 실행하면 중복 처리가 일어납니다. 그래서 HPA는 다중 인스턴스에서 안전하다고 확인된 서비스에만 적용하기로 했습니다.

레플리카가 2 이상일 때는 PDB(PodDisruptionBudget)로 `minAvailable: 1`을 두어, 노드 교체 같은 작업 중에도 최소 하나는 유지하게 합니다.

## 4. 도지커피 프로젝트의 구성

위의 해법을 합치면 도지커피 프로젝트의 클러스터는 다음과 같은 모습으로 설계되어 있습니다.

```text
관리형 쿠버네티스 클러스터 (프라이빗 노드)
 ├─ namespace: app
 │    ├─ dozy-auth        (replicas 1)
 │    ├─ dozy-wms-api
 │    ├─ dozy-inventory-api
 │    └─ dozy-catalog-api
 ├─ namespace: kafka
 │    └─ Kafka (StatefulSet, 단일 브로커)
 └─ namespace: observability
      ├─ Prometheus / Grafana
      └─ Loki / Tempo
```

몇 가지 선택의 이유는 다음과 같습니다.

- **관리형 쿠버네티스를 쓰는 이유**: 컨트롤 플레인을 클라우드가 운영해 주고, 노드까지 직접 관리하지 않는 방식을 고르면 학습 환경에서 관리 부담과 비용을 줄일 수 있습니다.
- **네임스페이스를 나누는 이유**: `app`, `kafka`, `observability`로 나누면 NetworkPolicy(Pod 사이 통신 허용 규칙)와 권한의 경계를 정하기 쉽습니다. 예를 들어 Kafka에는 `app` 네임스페이스에서만 접근하도록 제한할 수 있습니다.
- **Kafka를 클러스터 안에 직접 띄우는 이유**: 처음에는 단일 브로커를 StatefulSet(고정된 이름과 디스크가 필요한 워크로드를 위한 리소스)으로 띄워 시작하고, 이후 매니지드 Kafka로 바꿔 같은 부하 테스트를 반복해 비교할 계획입니다. 설정 값 하나만 바꿔 Kafka 구성을 전환할 수 있게 하고, 나머지 조건은 같게 맞춥니다.
- **관측 도구를 직접 설치하는 이유**: 학습이 목적이므로 관리형을 쓰지 않고 Prometheus(지표), Grafana(대시보드), Loki(로그), Tempo(분산 추적)를 직접 설치합니다. 요청 하나가 여러 서비스를 거치므로, 이 네 가지가 있어야 장애가 났을 때 원인을 따라갈 수 있습니다.

### 서비스마다 YAML을 쓰지 않기: 공통 Helm 차트

서비스마다 Deployment, Service, ConfigMap, probe, HPA 등을 따로 작성하면 같은 내용이 계속 반복되고, 공통 규칙을 바꿀 때 파일을 전부 고쳐야 합니다.

Helm은 쿠버네티스 리소스를 선언한 YAML 파일(매니페스트)을 템플릿으로 만들고, 값만 바꿔 배포하는 도구입니다. 이 템플릿 묶음을 차트라고 부릅니다.

그래서 이 프로젝트에서는 공통 Helm 차트 `dozy-service` 하나를 두고, 서비스마다 값만 다르게 주는 구조를 택했습니다.

```text
charts/dozy-service/        공통 차트 (Deployment, Service, probe, HPA, PDB ...)
releases/
  ├─ common.yaml            모든 서비스 공통 값
  ├─ auth.yaml              서비스별 값
  ├─ inventory.yaml
  ├─ wms.yaml
  └─ catalog.yaml
```

비루트 실행, JVM 힙 비율, graceful 종료 같은 공통 규칙은 차트의 기본값으로 두고, 서비스가 달라야 할 때만 values로 덮어씁니다. 새 서비스(예: Store)를 붙일 때는 차트를 새로 만들지 않고 `releases/store.yaml`과 배포 순서 항목을 추가하면 됩니다.

공통 차트는 잘못된 설정을 막는 안전장치로도 쓸 수 있습니다. 예를 들어 로컬 개발용 프로필은 인증을 우회하도록 만든 경우가 많으므로, 클라우드에서 그 프로필로 기동하면 배포 단계에서 실패하도록 검사를 넣을 수 있습니다.

## 5. 쿠버네티스가 해결해 주지 않는 것

쿠버네티스는 서비스를 "어떻게 실행하는가"를 해결합니다. 앞선 MSA 글에서 다룬 설계 문제는 그대로 남습니다.

| 문제           | 쿠버네티스가 하는 일                                                                | 여전히 서비스가 해야 하는 일                   |
| -------------- | ----------------------------------------------------------------------------------- | ---------------------------------------------- |
| 서비스 간 계약 | 호출할 수 있는 이름을 제공합니다.                                                   | API와 이벤트 계약을 정하고 호환성을 지킵니다.  |
| 중복 요청      | 없음. 재시작이나 롤링 업데이트 중에는 요청이 재시도될 수 있습니다.                  | 재시도에도 결과가 같도록 멱등하게 설계합니다.  |
| 데이터 일관성  | 없음                                                                                | Outbox, 보상 작업 같은 복구 흐름을 설계합니다. |
| 장애 전파      | 응답하지 못하는 Pod를 트래픽에서 제외합니다. 호출 지연이 번지는 것은 막지 못합니다. | 타임아웃, 재시도, 서킷 브레이커를 정합니다.    |

그리고 쿠버네티스를 도입하면서 새로 생기는 부담도 있습니다.

- **DB 커넥션**: wms의 커넥션 풀 최대치가 20이라면, Pod가 3개일 때 최대 60개의 연결이 필요합니다. `Pod 수 × 풀 크기`가 DB의 `max_connections` 안에 들어와야 합니다.
- **롤링 업데이트 중의 겹침**: auth는 replicas 1로 고정하지만, 롤링 업데이트 중에는 새 Pod와 기존 Pod가 잠시 함께 떠 있습니다. 스케줄 작업이나 인메모리 상태에 영향이 없는지 확인해야 합니다.
- **Kafka 단일 브로커**: 복제본이 없으므로 브로커가 내려가는 동안에는 발행과 소비가 모두 멈추고, 디스크를 잃으면 데이터도 잃을 수 있습니다. 학습 환경이라 허용했고, 이벤트는 inventory와 catalog의 Outbox로 다시 발행할 수 있다는 전제입니다.
- **비용**: 클러스터는 켜 두는 것만으로 비용이 듭니다. 그래서 예산 알림을 가장 먼저 설정하고, 사용하지 않을 때는 환경을 내리는 절차를 둡니다.

서비스가 4~5개인 규모에서 쿠버네티스가 꼭 필요한지는 따져 볼 만한 질문입니다. 이 프로젝트는 서비스 수보다는 **MSA의 운영을 직접 경험하고 학습하는 것**을 목적으로 도입합니다. 목적이 다르면 판단도 달라질 수 있습니다.

## 6. 정리

- MSA는 서비스 수만큼 배포, 복구, 주소 관리, 설정, 확장의 문제를 만듭니다.
- 쿠버네티스는 원하는 상태를 선언하면 그 상태를 유지하는 방식으로 이 문제들을 풉니다.
- Deployment는 롤링 업데이트와 롤백을, probe는 장애 감지와 복구를, Service는 고정된 이름을, Ingress는 외부 노출을 맡습니다.
- 설정은 ConfigMap, 비밀값은 클라우드의 비밀값 저장소와 External Secrets로 이미지 밖에서 주입합니다.
- 서비스가 늘어날수록 공통 Helm 차트와 서비스별 values로 반복을 줄일 수 있습니다.
- 쿠버네티스는 서비스 계약, 멱등성, 데이터 일관성 같은 설계 문제를 대신 해결하지 않습니다.
- 서비스마다 확장 조건이 다릅니다. Pod를 늘리기 전에 서비스가 다중 인스턴스에서 안전한지 먼저 확인해야 합니다.

다음에는 설계한 구성을 실제 클러스터에 올려 보며, 이 글에서 확인하지 못한 가정(JWKS 조회 경로, 관리형 쿠버네티스에서의 StatefulSet 동작 등)이 어떻게 되었는지 기록해 보겠습니다.
