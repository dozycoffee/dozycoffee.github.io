서비스가 커질수록 “다른 서비스의 기능을 호출한다”는 단순한 일도 복잡해집니다.

예를 들어 주문이 확정되면 재고를 차감하고, 알림을 보내고, 분석 데이터를 적재해야 한다고 가정해 보겠습니다. 주문 서비스가 이 모든 일을 HTTP 호출로 순서대로 처리하면, 재고 서비스나 알림 서비스가 잠시 느려진 것만으로 주문 요청 전체가 지연되거나 실패할 수 있습니다.

이 글에서는 `dozy-inventory-api`의 재고·예약 이벤트를 예시로, 메시지 큐가 필요한 이유와 Kafka가 메시지를 저장하고 전달하는 방식, 그리고 안전한 소비를 위해 알아야 할 `Offset Commit`, `Consumer Lag`, `Retry`, `DLQ`, `Idempotency`를 살펴보겠습니다.

> [!NOTE]
> 이 글의 범위는 Kafka를 처음 도입하거나 사용하는 개발자가 메시지 처리의 핵심 동작과 실패 대응을 이해하는 데 있습니다.

## 1. 메시지 큐란 무엇인가?

메시지 큐는 한 서비스가 만든 메시지를 저장해 두었다가, 다른 서비스가 나중에 읽어 처리하도록 연결하는 중간 통로입니다.

가령 주문이 생성된 뒤 재고를 예약해야 하는 상황을 생각해 보겠습니다.

### 직접 호출하는 방식

```text
Order Service ──HTTP 요청──> Inventory Service
      │
      ├─────────HTTP 요청──> Notification Service
      │
      └─────────HTTP 요청──> Analytics Service
```

이 방식은 처음에는 이해하기 쉽습니다. 하지만 서비스가 늘어나면 주문 서비스는 여러 서비스의 주소, 응답 형식, 장애 상황을 모두 알아야 합니다.

특히 재고 서비스가 일시적으로 장애인 경우 다음과 같은 선택지가 생깁니다.

- 주문 자체를 실패시킬 것인지 결정해야 합니다.
- 주문은 성공시키고 나중에 재고 처리를 다시 시도할지 결정해야 합니다.
- 재고는 성공했지만 알림 전송이 실패하면 어디까지 되돌릴지 결정해야 합니다.

동기 호출은 호출자가 응답을 기다리는 구조입니다. 따라서 뒤쪽 서비스의 처리 시간과 장애가 앞쪽 서비스에 쉽게 전파됩니다.

### 메시지 기반 통신 방식

```text
Order Service ──발행──> Message Broker <──소비── Inventory Service
                              │
                              ├──────────────> Notification Service
                              │
                              └──────────────> Analytics Service
```

주문 서비스는 “주문이 생성되었다”는 사실을 메시지로 발행하고, 각 서비스는 자신에게 필요한 메시지를 독립적으로 소비합니다.

이 방식의 장점은 다음과 같습니다.

- 생산자와 소비자의 결합도가 낮아집니다.
- 소비자가 잠시 중단되어도 메시지를 보관할 수 있습니다.
- 같은 이벤트를 여러 서비스가 각자의 목적에 맞게 처리할 수 있습니다.
- 처리량이 급증해도 소비자 수를 늘려 확장할 수 있습니다.

물론 메시지 큐가 모든 문제를 없애 주지는 않습니다. 비동기 처리에서는 “언제 처리 결과를 알 수 있는가”, “같은 메시지가 두 번 오면 어떻게 할 것인가”, “처리에 실패한 메시지는 어디로 갈 것인가”를 별도로 설계해야 합니다.

## 2. Kafka란 무엇인가?

Kafka는 이벤트 스트림을 저장하고 전달하는 분산 메시지 브로커입니다. 생산자는 메시지를 Kafka에 기록하고, 소비자는 원하는 위치부터 메시지를 읽습니다.

일반적인 큐를 우편함에 비유한다면, Kafka는 일정 기간 보관되는 추가 전용 로그에 가깝습니다. 소비자가 메시지를 읽었다고 해서 메시지가 즉시 사라지지 않습니다. 보관 기간 안이라면 다른 소비자가 같은 메시지를 읽거나, 장애 이후 특정 위치부터 다시 읽을 수 있습니다.

`dozy-inventory-api`는 재고 수량과 예약 상태가 변경될 때 이벤트를 Kafka로 발행합니다. 이를 구독하는 WMS, 매장 시스템 같은 서비스는 자신의 역할에 필요한 이벤트를 소비할 수 있습니다.

예를 들면 다음과 같은 흐름입니다.

```text
Inventory API
  └─ 재고 수량 변경 또는 예약 상태 변경
       └─ Kafka 이벤트 발행
            ├─ OMS: 주문 상태 또는 예약 상태 반영
            ├─ WMS: 출고·입고 작업 반영
            └─ Store: 매장 재고 정보 갱신
```

Kafka는 다음과 같은 상황에서 특히 잘 맞습니다.

- 하나의 도메인 이벤트를 여러 서비스가 구독해야 할 때
- 요청 처리와 후속 작업을 분리하고 싶을 때
- 이벤트를 다시 재생하거나, 처리 이력을 일정 기간 보관해야 할 때
- 높은 처리량을 병렬로 처리해야 할 때

반대로 즉시 결과가 꼭 필요한 단순 조회나 강한 일관성이 필요한 단일 트랜잭션 작업까지 Kafka로 바꿀 필요는 없습니다. 메시지 기반 설계는 운영과 실패 처리를 위한 추가 복잡도를 함께 가져옵니다.

## 3. Kafka의 핵심 구성 요소

Kafka를 이해할 때는 Producer, Consumer, Topic, Partition, Offset, Consumer Group의 관계를 먼저 잡는 것이 좋습니다.

```text
Producer
   │
   │ 메시지 발행
   ▼
Topic
 ├─ Partition 0: [0] [1] [2] [3]
 ├─ Partition 1: [0] [1] [2]
 └─ Partition 2: [0] [1] [2] [3] [4]
   │
   ▼
Consumer Group
 ├─ Consumer A → Partition 0
 ├─ Consumer B → Partition 1
 └─ Consumer C → Partition 2
```

### Producer

Producer는 Kafka에 메시지를 발행하는 애플리케이션입니다.

`inventory-api`에서는 재고, 예약, 상품 같은 집계의 상태가 바뀔 때 이벤트를 발행합니다. 이벤트에는 본문(payload)뿐 아니라 이벤트 ID, 이벤트 유형, 발생 시각 같은 메타데이터도 함께 담을 수 있습니다.

### Topic

Topic은 메시지를 분류하는 이름입니다. 데이터베이스의 테이블이나 이벤트 채널처럼 생각할 수 있습니다.

`inventory-api`는 집계 유형별로 토픽을 나누는 방식을 사용합니다.

```text
dozy.inventory.inventory
dozy.inventory.reservation
dozy.inventory.product
```

이렇게 나누면 구독자는 자신에게 필요한 도메인의 이벤트만 구독할 수 있습니다.

### Partition

Partition은 하나의 Topic을 여러 개의 로그로 나눈 단위입니다. Kafka의 병렬 처리와 순서 보장의 기준이기도 합니다.

중요한 규칙은 다음과 같습니다.

> 메시지 순서는 Topic 전체가 아니라 같은 Partition 안에서만 보장됩니다.

따라서 서로 순서가 보장되어야 하는 이벤트에는 같은 Key를 사용해야 합니다.

`inventory-api`의 재고 이벤트는 `창고 ID:상품 ID`를 키로 사용할 수 있습니다. 같은 창고의 같은 상품에 대한 재고 변경은 같은 Partition으로 향하게 되고, 그 안에서는 발행 순서를 유지할 수 있습니다.

```text
Key: warehouse-1:product-100

재고 +10  → Partition 2
재고 -3   → Partition 2
재고 +5   → Partition 2
```

반면 서로 다른 키는 다른 Partition으로 갈 수 있으므로, 두 키 사이의 처리 순서까지 보장할 수는 없습니다.

### Offset

Offset은 Partition 안에서 각 메시지의 위치를 나타내는 번호입니다.

```text
Partition 2

Offset:  0      1      2      3
       [입고]  [예약]  [출고]  [조정]
```

Consumer는 “어디까지 읽었는가”를 Offset으로 기록합니다. 장애가 발생했을 때 마지막으로 기록된 Offset 이후부터 다시 처리할 수 있는 이유도 여기에 있습니다.

### Consumer와 Consumer Group

Consumer는 Kafka 메시지를 읽고 처리하는 애플리케이션입니다. 같은 Consumer Group에 속한 Consumer들은 하나의 Partition을 나누어 맡습니다.

예를 들어 `reservation-worker` 그룹에 Consumer가 2개이고 Topic의 Partition이 3개라면, 최대 2개 Partition만 동시에 처리합니다. 반대로 Consumer가 5개여도 Partition이 3개라면 2개 Consumer는 할 일이 없습니다.

> 한 Consumer Group 안에서 병렬 처리의 최대치는 Partition 수를 넘을 수 없습니다.

다만 서로 다른 Consumer Group은 같은 Topic을 독립적으로 읽을 수 있습니다. OMS와 WMS가 같은 재고 이벤트를 각자 처리할 수 있는 이유입니다.

## 4. inventory-api의 메시지 처리 과정

이제 재고 예약을 예시로 메시지 하나가 이동하는 흐름을 따라가 보겠습니다.

```text
1. OMS가 재고 예약 요청
2. Inventory API가 가용 재고를 확인하고 예약 생성
3. ReservationChanged 이벤트 기록
4. Kafka Topic에 이벤트 발행
5. OMS 또는 WMS가 이벤트 소비
6. 각 서비스가 자신의 DB와 업무 상태 갱신
7. 성공한 위치까지 Offset Commit
```

예시 이벤트는 다음과 같은 형태가 될 수 있습니다.

```json
{
  "reservationId": "reservation-20261010-001",
  "warehouseId": "warehouse-seoul-01",
  "eventType": "RESERVATION_CREATED",
  "occurredAt": "2026-10-10T09:30:00Z",
  "items": [
    {
      "productId": "coffee-bean-001",
      "quantity": 3
    }
  ]
}
```

메시지 본문에는 비즈니스 데이터가 들어가고, Kafka 헤더에는 `event-id`, `event-type`, `aggregate-type`, `occurred-at`처럼 처리에 필요한 메타데이터를 둘 수 있습니다.

여기서 `event-id`는 매우 중요합니다. 네트워크 장애나 프로세스 종료가 발생하면 같은 이벤트가 다시 발행되거나 다시 소비될 수 있습니다. 소비자는 이 ID로 이미 처리한 이벤트인지 판단할 수 있어야 합니다.

## 5. Offset Commit과 메시지 전달 보장

Consumer가 메시지를 읽었다는 것과, 비즈니스 처리를 성공했다는 것은 다릅니다.

Kafka에서 Consumer는 메시지를 처리한 뒤 Offset을 Commit합니다. Commit은 “이 Partition의 여기까지 처리가 완료되었다”고 기록하는 행위입니다.

### Commit을 먼저 하면: At-most-once

```text
1. 메시지 수신
2. Offset Commit
3. 재고 처리
4. 애플리케이션 장애
```

이 경우 Offset은 이미 앞으로 이동합니다. 재고 처리가 끝나기 전에 장애가 나면 Kafka는 메시지를 다시 전달하지 않습니다. 메시지가 유실될 수 있지만 중복 처리 가능성은 낮습니다.

이를 **At-most-once**, 즉 “최대 한 번 전달”이라고 합니다.

### 처리 후 Commit하면: At-least-once

```text
1. 메시지 수신
2. 재고 처리 성공
3. Offset Commit 전에 애플리케이션 장애
4. 재시작 후 같은 메시지 재수신
```

이 경우 메시지는 다시 전달될 수 있습니다. 메시지 유실 가능성은 낮아지지만 중복 처리가 발생할 수 있습니다.

이를 **At-least-once**, 즉 “최소 한 번 전달”이라고 합니다.

대부분의 비즈니스 이벤트 처리에서는 유실보다 중복이 더 안전합니다. 그래서 보통은 처리 성공 후 Offset을 Commit하고, 소비자가 중복 메시지를 안전하게 처리하도록 설계합니다.

### Auto Commit과 Manual Commit

Auto Commit은 일정 간격으로 Offset을 자동 저장합니다. 구현은 간단하지만 실제 처리 성공 시점과 Commit 시점이 어긋날 수 있습니다.

Manual Commit은 애플리케이션이 비즈니스 작업 성공을 확인한 뒤 직접 Offset을 기록합니다. 실패 처리와 재시도 정책을 명확히 통제해야 하는 Consumer라면 이 방식이 더 적합합니다.

### Exactly-once를 오해하지 않기

Kafka에서 Exactly-once는 특정 조건에서 Kafka 내부의 읽기·쓰기 처리를 한 번처럼 보이게 만드는 기능입니다. 하지만 이것이 외부 DB 작업까지 자동으로 정확히 한 번 실행해 준다는 뜻은 아닙니다.

예를 들어 Consumer가 다음을 수행한다고 가정해 보겠습니다.

```text
Kafka 메시지 소비
  └─ 외부 DB에 재고 이력 저장
      └─ Offset Commit
```

DB 저장에는 성공했지만 Offset Commit 전에 장애가 발생하면 메시지는 다시 전달됩니다. DB에 이미 기록한 작업을 구분하지 못하면 이력이 중복 저장될 수 있습니다.

따라서 외부 DB, HTTP API, 이메일 발송처럼 Kafka 밖에 영향을 주는 작업에서는 멱등성 설계가 필요합니다.

## 6. Consumer Lag과 메시지 처리 성능

Consumer Lag은 Kafka에 쌓인 메시지 중 Consumer가 아직 처리하지 못한 양입니다.

```text
Partition 최신 Offset: 10,000
Consumer Commit Offset: 9,200

Consumer Lag: 800
```

Lag 자체가 항상 문제는 아닙니다. 순간적으로 주문이 몰리면 일시적으로 증가할 수 있습니다. 다만 계속 증가한다면 생산 속도가 소비 속도보다 빠르다는 뜻입니다.

재고 이벤트가 계속 쌓이는 상황을 가정해 보겠습니다.

```text
Producer 발행 속도: 초당 1,000건
Consumer 처리 속도: 초당 600건

매초 Lag 증가량: 약 400건
```

이때 확인할 사항은 다음과 같습니다.

- Consumer의 비즈니스 처리나 외부 DB 조회가 느린지
- 특정 Partition에만 메시지가 몰렸는지
- Consumer 수가 Partition 수보다 적은지
- Broker 또는 네트워크에 병목이 있는지
- 재시도가 반복되어 처리 시간이 길어졌는지

대응 방법도 원인에 따라 달라집니다.

| 원인                      | 우선 고려할 대응                        |
| ------------------------- | --------------------------------------- |
| Consumer 처리 자체가 느림 | DB 쿼리, 외부 호출, 배치 처리 방식 개선 |
| Consumer 수 부족          | Partition 수 범위 안에서 Consumer 확장  |
| 특정 Key에 이벤트 집중    | Key 설계와 Partition 분산 검토          |
| 일시적인 트래픽 급증      | 처리량 확장, Lag 알림 기준 조정         |
| 반복 실패 메시지          | Retry 정책과 DLQ 확인                   |

Partition을 무작정 늘리는 것이 항상 해결책은 아닙니다. 같은 키의 순서 보장 범위가 달라지고, 키 쏠림이 있으면 Partition 수가 많아도 특정 Partition만 계속 밀릴 수 있습니다.

운영에서는 Topic별, Consumer Group별 Lag을 지속적으로 관찰해야 합니다. 특히 “Lag이 얼마나 큰가”뿐 아니라 “얼마나 오래 증가하는가”가 중요합니다.

## 7. 메시지 처리 실패 대응: Retry, DLQ, Idempotency

메시지 처리는 실패를 전제로 설계해야 합니다. 재고 DB가 잠시 느려질 수도 있고, 잘못된 데이터가 들어올 수도 있으며, 외부 서비스가 응답하지 않을 수도 있습니다.

### 일시적 오류와 영구적 오류를 구분합니다

일시적 오류는 잠시 뒤 다시 시도하면 성공할 가능성이 있습니다.

- DB 연결 일시 장애
- 네트워크 타임아웃
- 외부 서비스의 일시적인 5xx 오류

영구적 오류는 같은 입력으로 재시도해도 성공할 가능성이 낮습니다.

- 필수 필드 누락
- 지원하지 않는 이벤트 버전
- 이미 삭제된 참조 데이터
- 비즈니스 규칙 위반

모든 실패를 즉시 무한 재시도하면 장애가 더 커질 수 있습니다. 오류 종류에 따라 Retry와 DLQ를 분리해야 합니다.

### Retry와 Backoff

일시적 오류라면 바로 연속해서 재시도하기보다 일정 시간 기다리는 Backoff를 둡니다.

```text
1차 실패 → 1초 후 재시도
2차 실패 → 5초 후 재시도
3차 실패 → 30초 후 재시도
최종 실패 → DLQ 이동
```

이 방식은 장애가 난 DB나 외부 서비스에 과도한 부하를 주지 않습니다.

다만 Retry는 순서와도 관련이 있습니다. 같은 키의 이벤트가 다음 순서로 들어왔다고 가정해 보겠습니다.

```text
재고 +10 → 예약 -3 → 출고 -2
```

중간의 `예약 -3` 처리에 실패했다고 해서 뒤의 `출고 -2`를 먼저 처리하면 상태가 꼬일 수 있습니다. 순서가 중요한 이벤트라면 실패 메시지를 건너뛰고 다음 메시지를 처리하는 정책을 신중히 선택해야 합니다.

`inventory-api`의 Outbox 발행 규칙도 이 문제를 고려합니다. 같은 파티션 키의 앞선 이벤트 발행이 실패하면 뒤의 이벤트를 섣불리 진행하지 않습니다. 순서를 지키는 대신 해당 이벤트 묶음의 처리가 잠시 멈출 수 있습니다.

### Dead Letter Queue, DLQ

정해진 횟수만큼 재시도해도 처리할 수 없는 메시지는 별도 Topic으로 옮겨 보관합니다. 이것이 DLQ입니다.

```text
inventory 이벤트 Topic
  └─ Consumer 처리 실패
       └─ Retry 실패
            └─ inventory 이벤트 DLQ
```

DLQ는 실패 메시지를 버리는 장소가 아닙니다. 원본 메시지, 실패 원인, 재시도 횟수, 최초 수신 시각 등을 남겨 두고 운영자가 원인을 분석하고 복구할 수 있게 하는 장소입니다.

DLQ에 쌓인 메시지는 다음 절차로 다룰 수 있습니다.

1. 실패 원인을 확인합니다.
2. 데이터 문제라면 데이터를 수정하거나 이벤트 계약을 보완합니다.
3. 코드 문제라면 배포 후 재처리합니다.
4. 재처리해도 해결되지 않는 경우 비즈니스적으로 보정합니다.

DLQ 메시지를 본 Topic으로 무작정 되돌리면 같은 실패가 반복될 수 있습니다. 재처리 전에는 실패 원인이 해결되었는지 먼저 확인해야 합니다.

### Idempotency: 같은 메시지가 여러 번 와도 안전하게 처리합니다

At-least-once 전달에서는 중복 메시지가 정상적인 상황입니다. 따라서 Consumer는 같은 메시지를 두 번 받아도 결과가 한 번 처리한 것과 같아야 합니다. 이를 멱등성(Idempotency)이라고 합니다.

`inventory-api`가 발행하는 이벤트에는 고유한 `event-id`를 둘 수 있습니다. Consumer는 이 값을 처리 이력 테이블에 저장하고, 이미 처리한 이벤트라면 작업을 건너뜁니다.

```text
1. event-id = evt-123 수신
2. 처리 이력에 evt-123이 있는지 확인
3. 없으면 비즈니스 처리 + evt-123 기록
4. 있으면 이미 처리한 이벤트로 판단하고 종료
```

구현할 때는 “조회 후 저장”을 단순히 분리하기보다, 이벤트 ID에 유니크 제약을 두는 것이 안전합니다. 여러 Consumer 인스턴스가 동시에 같은 메시지를 처리하려는 경쟁 상황도 막아야 하기 때문입니다.

```sql
create table processed_event (
  event_id varchar(64) primary key,
  processed_at datetime not null
);
```

또한 멱등성은 이벤트 전체가 아니라 실제 부작용까지 고려해야 합니다.

- DB 상태 변경은 이벤트 ID 또는 비즈니스 키를 기준으로 중복을 방지해야 합니다.
- 외부 API 호출은 상대 API의 idempotency key 지원 여부를 확인해야 합니다.
- 이메일·푸시 발송은 발송 요청 ID를 기록하거나 중복 발송 허용 여부를 결정해야 합니다.
- 재고 차감은 단순 누적 연산보다 요청 ID 기반의 이력과 상태 전이로 관리하는 편이 안전합니다.

## 8. 정리: Kafka를 사용할 때 고려할 점

Kafka는 서비스 간 결합도를 낮추고, 이벤트를 안전하게 전달하며, 처리량을 확장하는 데 유용합니다. 하지만 Kafka를 도입하는 순간 실패, 중복, 순서, 관측 가능성까지 함께 설계해야 합니다.

`inventory-api` 사례를 통해 핵심을 정리하면 다음과 같습니다.

- Topic은 이벤트의 분류 단위이고, Partition은 병렬 처리와 순서 보장의 단위입니다.
- 같은 순서가 필요한 재고·예약 이벤트는 같은 Key로 같은 Partition에 보내야 합니다.
- Offset Commit 시점에 따라 메시지 유실과 중복 처리의 가능성이 달라집니다.
- 일반적인 비즈니스 Consumer는 At-least-once를 전제로 멱등하게 설계하는 편이 안전합니다.
- Consumer Lag은 메시지 적체를 보여 주는 핵심 지표이며, 증가 추세와 원인을 함께 봐야 합니다.
- 일시적 오류는 Backoff를 둔 Retry로, 반복되거나 영구적인 오류는 DLQ로 분리해 대응합니다.
- Kafka의 Exactly-once와 외부 DB 작업의 “정확히 한 번 실행”은 같은 문제가 아닙니다.
