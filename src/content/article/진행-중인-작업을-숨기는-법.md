# 미완성 작업을 배포해도 괜찮을까?

기능을 완성하는 데 며칠이 걸린다면 그동안 작성한 코드는 어디에 두어야 할까요? 별도 브랜치에 모아두면 사용자에게 노출되지 않지만, 작업이 길어질수록 메인 브랜치와의 차이도 커져요. 반대로 메인 브랜치에 자주 합치면 아직 끝나지 않은 기능이 운영 환경에 들어갈 수 있죠.

이 글에서는 발렌티나 세르빌의 [《Continuous Deployment》](https://www.thoughtworks.com/en-us/insights/books/continuous-deployment)를 읽으며 정리한 **진행 중인 작업을 숨기는 방법**을 이야기해볼게요. 브랜치로 코드를 분리하는 방식부터, 코드를 배포하되 실행하거나 공개하지 않는 기능 토글과 확장·축소 패턴까지 살펴보려고 해요.

## 지속적 배포에서 작업을 작게 나누는 이유

지속적 배포는 변경 사항이 검증 절차를 통과하면 별도의 수동 배포 단계를 기다리지 않고 운영 환경에 배포하는 방식이에요. 이때 **배포**와 **공개**는 같은 일이 아니에요. 새 코드가 운영 환경에 있어도 사용자가 그 기능을 이용할 수 없도록 할 수 있죠.

저자는 배포를 기다리는 코드를 재고에 비유해요. 변경 사항이 오래 쌓이면 작성 당시의 맥락을 다시 파악해야 하고, 그동안 달라진 메인 브랜치와 코드를 맞추는 데에도 시간이 들어요. 작은 변경을 자주 통합하면 이런 간격을 줄이고, 문제가 생겼을 때 어떤 변경에서 시작됐는지도 좁혀볼 수 있어요.

하지만 자주 통합하려면 미완성 코드가 기존 기능을 깨뜨리지 않아야 해요. 그래서 중요한 질문은 **작업이 끝날 때까지 코드를 어디에 숨길지**, 그리고 **운영 환경에 들어간 뒤에도 어떻게 사용자의 실행 경로에서 분리할지**예요.

## 브랜치에 작업을 숨기기

가장 익숙한 방법은 메인 브랜치에서 기능 브랜치를 만들어 작업하는 거예요. 예를 들어 `feature/a`와 `feature/b`에서 각각 개발하다가 완성된 코드를 메인 브랜치에 합칠 수 있어요. 이 기간에는 미완성 코드가 메인 브랜치에 들어가지 않으므로 운영 환경에서도 실행되지 않죠.

다만 브랜치를 오래 유지하면 통합 비용이 커질 수 있어요. 메인 브랜치의 코드가 바뀌는 동안 기능 브랜치도 따로 발전하기 때문이에요. 같은 부분을 수정했다면 충돌을 해결해야 하고, 충돌이 없더라도 두 변경이 함께 동작하는지 다시 확인해야 해요.

브랜치가 짧고 변경 범위가 작다면 충분히 유용한 방식이에요. 작업이 길어지는 경우에는 브랜치에 모든 변경을 쌓아두기보다, 안전하게 나눌 수 있는 부분부터 메인 브랜치에 통합할 방법을 생각해볼 수 있어요.

## 기능 토글로 실행을 숨기기

기능 토글은 새 코드의 실행 여부를 조건으로 제어하는 방식이에요. 코드는 배포하되 토글을 꺼두면 사용자는 기존 실행 경로를 이용해요.

```java
if (newFeatureEnabled) {
    return newFeature.execute();
}

return existingFeature.execute();
```

이렇게 하면 기능을 한 번에 완성하지 않아도 코드를 조금씩 통합할 수 있어요. 기능이 준비된 뒤에는 내부 사용자나 QA 담당자에게만 토글을 켜서 확인하고, 대상을 점차 늘릴 수도 있죠. 사용자를 나누어 다른 경험을 제공하는 A/B 테스트에도 활용할 수 있어요.

대신 토글이 있는 동안에는 켜진 경우와 꺼진 경우를 모두 관리해야 해요. 두 실행 경로를 테스트해야 하고, 누가 토글을 바꿀 수 있는지와 현재 상태가 무엇인지도 알아야 하죠. 더 이상 필요하지 않은 토글을 그대로 두면 분기와 테스트 경우의 수가 계속 늘어나므로, 기능 공개가 끝나면 토글과 이전 코드를 제거하는 작업까지 계획해야 해요.

> [!TIP] 정적 기능 토글
> 환경 변수나 설정 파일을 읽어 애플리케이션 시작 시 토글 상태를 정할 수도 있어요. 별도의 토글 서비스를 운영할 필요가 적지만, 상태를 바꾸려면 설정을 갱신하고 애플리케이션을 다시 시작하거나 배포해야 할 수 있어요.
>
> 실행 중 상태를 바꾸는 방식은 빠르게 대상을 조절할 수 있어요. 다만 토글 상태를 제공하는 시스템의 장애나 지연에 대비해, 값을 캐시하거나 조회에 실패했을 때 어떤 상태를 사용할지 정해야 해요.

토글을 껐다고 해서 새 코드가 무조건 안전해지는 것은 아니에요. 애플리케이션 시작 시 실행되는 코드나 데이터베이스 스키마 변경처럼 조건문 바깥에 영향을 주는 작업은 별도로 확인해야 해요.

## 확장·축소로 기존 경로를 유지하기

확장·축소 패턴은 **기존 경로를 유지한 채 새 경로를 추가하고, 사용처를 옮긴 뒤 이전 경로를 제거**하는 방식이에요. 병렬 변경이라고도 불러요.

예를 들어 기존 `Calculator`를 `NewCalculator`로 바꿔야 한다고 해볼게요. 모든 코드를 한 번에 교체하는 대신 세 단계로 나눌 수 있어요.

1. **확장**: 기존 `Calculator`는 그대로 두고 `NewCalculator`와 필요한 결과 형식을 추가해요. 아직 기존 호출부는 바꾸지 않아요.
2. **이전**: 호출부를 하나씩 `NewCalculator`로 옮겨요. 기존 코드와 새 코드가 함께 존재하는 동안에는 두 경로가 기대한 결과를 내는지 확인해요.
3. **축소**: 더 이상 `Calculator`를 사용하는 곳이 없음을 확인한 뒤 이전 구현과 불필요한 호환 코드를 제거해요.

```text
기존:   호출부 A, B → Calculator
확장:   호출부 A, B → Calculator     NewCalculator 추가
이전:   호출부 A    → NewCalculator  호출부 B → Calculator
축소:   호출부 A, B → NewCalculator  Calculator 제거
```

새 구현을 추가한 시점에는 기존 호출부가 그대로이므로, 새 경로가 미완성이어도 기존 계산 흐름을 바꾸지 않을 수 있어요. 다만 호출부를 옮기는 순간부터는 새 코드가 실제로 실행돼요. 이때는 결과의 호환성, 오류 처리, 되돌릴 방법을 확인해야 하죠.

이 패턴은 실행 코드뿐 아니라 API나 데이터베이스 스키마를 바꿀 때도 유용해요. 새 필드를 먼저 추가하고, 읽고 쓰는 코드를 순서대로 옮긴 뒤, 더 이상 사용하지 않는 필드를 삭제하는 식이에요. 이전 단계가 끝나기 전에 기존 필드를 지우면 아직 업데이트되지 않은 코드가 실패할 수 있어요.

확장·축소가 언제나 기존 코드를 처음부터 다시 작성하라는 뜻은 아니에요. 핵심은 새 구조를 먼저 받아들일 수 있게 만들고, 사용처를 안전하게 이전한 다음, 이전 구조를 정리하는 순서에 있어요.

## 어떤 방법을 선택할까?

세 방법은 작업을 숨기는 위치가 달라요.

| 방법        | 숨기는 위치                                       | 살펴볼 점                                               |
| ----------- | ------------------------------------------------- | ------------------------------------------------------- |
| 기능 브랜치 | 메인 브랜치 밖에 코드를 둬요.                     | 오래 유지할수록 통합과 검증 비용이 커질 수 있어요.      |
| 기능 토글   | 배포된 코드 안에서 실행·공개 여부를 제어해요.     | 토글의 두 상태를 관리하고, 사용이 끝나면 제거해야 해요. |
| 확장·축소   | 기존 경로를 유지하면서 새 경로를 병렬로 추가해요. | 사용처를 옮기는 순서와 호환성을 확인해야 해요.          |

짧은 작업이라면 브랜치에서 완성한 뒤 합쳐도 돼요. 기능을 조금씩 배포하면서 공개 시점을 따로 정해야 한다면 토글이 도움이 돼요. 기존 구현이나 계약을 여러 사용처가 공유한다면 확장·축소로 이전 단계를 나누는 편이 안전할 수 있고요. 한 작업에서 토글과 확장·축소를 함께 쓰는 것도 가능해요.

결국 목표는 **작은 변경을 자주 통합하면서도, 아직 준비되지 않은 동작을 사용자에게서 분리하는 것**이에요. 어떤 방식을 택하든 기존 기능의 테스트와 새 경로의 검증, 그리고 임시로 남긴 분기를 정리하는 작업까지 포함해야 안전하게 다음 변경을 이어갈 수 있어요.
